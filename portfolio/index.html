무빙

FE·BE 코드잇 부트캠프 Part 4

이사 견적 요청·매칭, 실시간 채팅, 리뷰·커뮤니티, 관리자 운영을 다루는 이사 견적 매칭 서비스 · 담당: 견적요청·알림

A. 헤더 인증을 유지하는 실시간 알림 (FE)

알림을 SSE로 받기로 했지만 앱 인증은 Authorization: Bearer 헤더인데 브라우저 EventSource는 커스텀 헤더를 실을 수 없었습니다. 토큰을 URL에 실으면 접근 로그·프록시에 남고, 짧게 만료되는 access token의 재발급을 자동 재연결 안에 끼워 넣기도 어려웠습니다.

  • fetch와 response.body.getReader()로 SSE 응답을 직접 읽는 클라이언트를 구현하고, 청크 경계·CRLF·EOF까지 처리하는 이벤트 파서와 zod 스키마 검증을 작성했습니다. 파싱에 실패한 이벤트는 에러 콜백만 부르고 스트림은 유지합니다.
  • 첫 401에서만 토큰을 재발급해 1회 재시도하고, 그 외 끊김은 지수 백오프로 재연결하며 재연결 성공 시 유실 가능성이 있는 목록을 다시 맞추는 것을 하나의 연결 수명주기로 묶었습니다. 세션당 스트림은 1개만 유지하고 로그아웃 시 즉시 끊습니다.
  • CRLF·청크 경계·EOF 파싱, 401 재시도, 백오프, 캐시 무효화 분기를 단위 테스트로 고정했습니다.

B. 대량 알림을 요청 경로에서 분리한 Outbox 워커 (BE)

견적을 제출하면 조건에 맞는 모든 기사(수백~수천 명)에게 알림을 보내야 하는데, 초기에는 제출 API 안에서 직접 생성해 제출 응답이 대량 처리에 묶이고, 중간 실패 시 일부 기사만 알림을 받는 문제가 있었습니다.

  • 제출은 조건부 원자 업데이트 1건과 NotificationOutbox enqueue 1건만 수행하게 하고, (jobType, sourceId) unique로 재시도·재제출에도 잡이 1건으로 수렴하게 했습니다.
  • node-cron 워커가 FOR UPDATE SKIP LOCKED로 잡을 원자적으로 claim하고, 기사 200명 단위 커서 청크로 나눠 처리한 뒤 claim당 상한에 도달하면 커서를 남기고 양보해 다음 틱이 이어받게 했습니다.
  • attempts 상한(5회) 후 FAILED와 lastError 기록, 5분 경과 stale 잡 재claim, 한 틱 내 실패 잡 제외로 중복 실행·부분 실패·무한 재시도를 다뤘습니다.

결과

제출 응답이 대량 알림 발송에서 분리됐고, 워커가 재시작하거나 중간에 실패해도 커서와 attempts 기준으로 이어서 재개됩니다. 토큰을 URL에 노출하지 않고 헤더 인증을 유지한 채 실시간 알림을 수신하며, 토큰 만료·네트워크 순단은 사용자 개입 없이 복구됩니다. 팀 공통 작업으로 GitHub Actions와 PM2 기반 배포 파이프라인도 구성해 main 병합 시 EC2 반영을 자동화했습니다.

배운 점

표준 API가 요구사항과 맞지 않으면 우회보다 한 단계 낮은 API로 내려가는 선택지가 있다는 것, 그리고 외부로 나가는 대량 작업은 재시도·중복·부분 실패를 전제로 요청 경로에서 분리해 설계해야 한다는 기준을 갖게 되었습니다.

최애의 포토

Frontend 코드잇 부트캠프 Part 3

아이돌·스타·일러스트 디지털 포토카드를 사고팔고 교환하는 컬렉션 플랫폼 · 담당: 마이갤러리 · 포토카드 생성

A. 필터 변경 시 리렌더 범위 축소

마이갤러리에서 필터를 바꾸면 목록뿐 아니라 상단 요약과 필터 UI까지 리렌더됐고, 페이지 레벨 로딩 분기 때문에 재조회마다 필터 UI가 리마운트되어 드롭다운 열림 상태와 입력 포커스가 끊겼습니다.

  • React.memo로 증상을 막는 대신, 원인이 "필터 상태가 최상위에 있는 구조"라고 보고 필터·검색·페이지 상태와 목록 쿼리를 MyGalleryCardSection으로 내리는 상태 콜로케이션을 택했습니다.
  • 로딩 처리를 목록 영역 안으로 국소화하고 초기 로딩(isLoading)과 값 보유 상태의 재조회(isFetching)를 구분해, 재조회 중에도 필터·검색 UI가 마운트를 유지하게 했습니다.

B. 월 생성 횟수 제한의 정합성

월 생성 한도의 잔여 횟수를 마이갤러리와 생성 폼 두 곳에 표시하고 소진 시 막아야 했는데, 카드 생성 직후에도 잔여 표시가 갱신되지 않아 새로고침이 필요했습니다.

  • 잔여·한도의 단일 소스인 백엔드 me 응답을 두 화면이 함께 조회하게 하고, 소진 시 버튼 클릭·폼 제출·서버 응답 3단계로 게이팅했습니다. 클라이언트 검사는 UX용, 최종 판정은 서버로 두었습니다.
  • 에러 코드별 처리 방식을 ERROR_HANDLER 테이블로 중앙화하고, 갱신 누락의 원인이 생성 mutation이 me 쿼리를 무효화하지 않던 것임을 확인해 무효화 대상에 추가했습니다.

결과

필터 변경 시 리렌더가 목록 영역으로 한정되고 필터 UI의 상태가 유지됩니다. 잔여 표시가 두 화면에서 일치하며, 잔여가 없으면 클릭·제출·서버 응답 어느 지점에서도 생성이 진행되지 않고 생성 직후 새로고침 없이 잔여 횟수가 갱신됩니다.

배운 점

리렌더 범위는 상태의 위치가 결정하고, 서버 상태 캐시의 정확성은 무엇을 언제 무효화하느냐가 결정한다는 것을 설계 기준으로 삼게 되었습니다. 주강사 총평에서는 이 프로젝트에서 FE·BE 양쪽에 걸쳐 100커밋 이상을 기록해 팀 내 최다 기여였다는 언급을 받았습니다.

FE·BE 코드잇 부트캠프 Part 2

스터디 개설·상세, 오늘의 습관 토글, 집중 타이머를 제공하는 학습 관리 서비스 · 담당: 스터디 상세·목록 · 최근 조회 · 응원 이모지

최근 조회한 스터디: 낡은 스냅샷과 N개 쿼리

최근 본 스터디를 객체 통째로 localStorage에 저장해 홈에서 그대로 보여주다 보니, 저장 이후 바뀐 포인트·이모지가 반영되지 않고 삭제된 스터디도 계속 노출됐습니다. 서버에서는 id마다 findUniqueOrThrow를 Promise.all로 실행해, id 개수만큼 쿼리가 나가고 하나만 없어도 응답 전체가 실패했습니다.

  • localStorage에는 id만 최근순으로 저장하고, 홈 진입 시 GET /studies/recent?ids=로 서버의 최신값을 조회하도록 표시값의 출처를 서버로 옮겼습니다.
  • 백엔드는 findMany({ id: { in } }) 단일 쿼리로 바꾸고, in 결과가 순서를 보장하지 않으므로 입력 순서를 애플리케이션에서 재구성하며 삭제된 스터디는 걸러냅니다.
  • 빈 localStorage에서는 요청을 보내지 않고(FE), ids가 없으면 빈 배열로 응답(BE)하도록 양쪽에서 방어했습니다.

결과

최근 목록이 저장 시점이 아닌 조회 시점의 서버 값으로 표시되고, id 개수와 무관하게 쿼리 1회로 처리되며 일부 스터디가 삭제돼도 나머지는 정상 응답합니다.

배운 점

클라이언트가 들고 있는 파생 데이터는 식별자만 두고 표시값은 조회 시점의 서버 상태에서 받아야 낡지 않는다는 것, 여러 건 조회의 개별 루프는 쿼리 수와 실패 전파를 함께 키운다는 것을 기준으로 삼게 되었습니다.
